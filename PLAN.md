# ng-material-theme — Working Plan

_Supersedes REDESIGN_PLAN.md (see git history). The code is the source of truth for direction._

## What we are building

A framework-free theming library where the browser is the theme engine.

- A theme is a handful of input variables (a light and a dark primary, optionally more).
- Everything else is derived in CSS with `light-dark()`, `oklch(from …)` and `color-mix()`.
- Any element can carry `theme="name"` and re-derive the whole palette for its subtree (sub-theming).
- Theme data can come from anywhere (a stylesheet, a database row, user input) because it is just a few variables.
- Angular Material is a consumer, reached through an adapter computed at Sass build time from Material's own role tables. It is not a runtime dependency.
- Typography is left to the consumer (Material apps use `mat.theme()`). The library ships a size scale with a density multiplier; Material component density also comes from `mat.theme()`.

## Guiding rules

1. **KISS.** Plain CSS and Sass, static HTML docs, and TypeScript for everything that is code: the switcher, the test runner, the docs build script. Scripts run directly under Node 24 (type stripping), so tooling has no compile step. No frameworks in the library or the docs site. Never `.js` or `.mjs`.
2. **Teach in dependency order.** Every docs chapter uses only concepts taught in earlier chapters. The build enforces it.
3. **Docs run the real library.** Every example is a standalone page rendered live in the docs, and the source shown beside it is that same file, pulled in at build time so they cannot drift.
4. **Derive what Material owns.** The adapter reads Material's own role tables at build time; nothing role-by-role is hand-maintained.
5. **Keep animation, register little.** Only the theme inputs are registered with `@property` (the twelve `--theme--{light,dark}--color--<palette>` inputs and the theme-level tuning variables). Derived tokens stay unregistered, so a theme change crossfades because derived values are re-substituted from the animating inputs every frame.

## Release management: cpdevtools/git-flow

Releases are run by [cpdevtools/git-flow](https://github.com/cpdevtools/git-flow), set up from [git-flow-template](https://github.com/cpdevtools/git-flow-template). Nothing release-related is hand-written here.

- **Versioning.** Every manifest carries the placeholder `0.0.0-MAIN`. The real version lives in `.publish/versions.yml` and is set with `pnpm gitflow version`. git-flow stamps it at build time.
- **Branches.** A branch without a slash is a mainline and publishes stable releases. A branch with a slash is a development line and only ever publishes prereleases. The rewrite therefore moves from `ng21` to `feature/ng21`, which publishes `21.0.0-feature.ng21` prereleases (git-flow adds a build suffix on repeats). `main` stays as it is until graduation.
- **Flow.** Every push keeps a draft release PR current. Merging that PR builds, packs and publishes. Tests run on every push via the `test` action, which calls each workspace project's `github.actions.build` and `github.actions.test` scripts, so those exact script names must exist (a project without them passes silently).
- **Graduation.** `main` has only ever published `-dev` prereleases, so there is no stable line to preserve and no LTS branch to cut. When the rewrite is ready: merge `feature/ng21` into `main`, set `.publish/versions.yml` to `21.0.0`, merge the release PR. Before that, merge `main` into the feature branch periodically, never the other way.
- **Docs deploy.** git-flow has no static-site target, so one small extra workflow, `docs-pages.yml`, builds `projects/docs` and deploys to GitHub Pages on push to `release/main` only. Feature-line releases do not publish docs.
- **Secrets.** `NPM_TOKEN` (already in the repo) for npmjs. `GITHUB_TOKEN` is used to install `@cpdevtools/*` from GitHub Packages, which the existing `.npmrc` line already covers.

## Phase 1 — Patch the holes in the colour system

Goal: sub-theming semantics are settled, every variable that is read is defined, and runtime colours are always readable.

- [x] **Cascade and inheritance rules for `core()`.**
      (a) Everything `core()` emits sits under zero-specificity selectors (`:where(:root)`, `:where(:root, [theme])`), so any user, `createTheme` or `defineTheme` rule wins regardless of stylesheet order.
      (b) `core()` never declares the primary/error inputs or the tuning variables. Their defaults are the `@property` initial values, so a nested `[theme]` inherits every input it does not set.
      (c) The four derived palettes (secondary, tertiary, neutral, neutral-variant) are declared as `oklch(from var(--theme--…--primary) …)` in `:where(:root, [theme])`, so a nested theme re-derives them from its (possibly inherited) primary unless it sets them explicitly.
      (d) `core()` emits `:where(:root) { color-scheme: light dark; }`, so the OS preference applies with no JavaScript.
      (e) `--elevation-shadow-color` becomes a plain `#000`.
      (f) Constants with nothing to re-derive (`--elevation-shadow-color`, `--theme--size-base--N`) are declared on `:where(:root)` only, never on `[theme]`, so a user or parent-theme override reaches nested themes; the dependent `--elevation-N` and `--theme--size--N` stay on `:where(:root, [theme])` so they re-resolve per theme.
- [x] **Surface roles via a tone function.** Add one Sass function `tone($input, $T)` returning `oklch(from <input> <L> calc(min(c, 0.27) * <k>) h / 1)`, where L maps Material's tone T (CIELAB L*) to OKLab L, with L = (T+16)/116 for T > 8 else cbrt(T/903.3), and k = min(1, 4·L·(1−L)) (both precomputed in Sass). k alone does not keep chroma in gamut: a wide-gamut input (rec2020 red has OKLCH chroma ≈ 0.36) keeps nearly all of it at mid tones, sRGB clipping then collapses the lightness and on-surface drops below 4.5:1, so chroma is capped at 0.27 first. Alpha is pinned to 1 here and in the four derived palettes, so a translucent input never makes surfaces translucent. `core()` emits, per mode wrapped in `light-dark()`, Material's tone numbers (light / dark) from the neutral (n) or neutral-variant (nv) input:
      surface n98/n6, surface-dim n87/n6, surface-bright n98/n24, surface-container-lowest n100/n4, -low n96/n10, surface-container n94/n12, -high n92/n17, -highest n90/n22, on-surface n10/n90, surface-variant nv90/nv30, on-surface-variant nv30/nv90, outline nv50/nv60, outline-variant nv80/nv30. `--color--background` and `--color--on-background` alias surface and on-surface. These are emitted by `core()` in `:where(:root, [theme])`, not by the adapter, so `core.css` alone defines them.
- [x] **Contrast from WCAG luminance.** The current step function thresholds OKLab L, which cannot guarantee AA for every hue. Change the contrast base to `color(from var(--c) srgb-linear S S S)` with `S = clamp(0, (0.179 - (0.2126 * r + 0.7152 * g + 0.0722 * b)) * 1e6, 1)`, which picks black or white at the exact luminance crossover (at least 4.58:1 against any colour). Contrast mixes use `color-mix(in oklab, …)`. Compute each variant's contrast per mode from the `--theme--light/dark--color--X-<variant>` intermediates and wrap the pair in `light-dark()`, so no joined token is ever a relative-colour origin. Delete `calculate-optimal-contrast`, `_contrast-utils.scss`, the Sass `contrast:` config key and the `--contrast--base` declarations in `createTheme`; Sass and CSS themes then pick the same on-colour. Guarantees, stated in the Variants chapter: `--contrast--high` ≥ 4.5:1, `--contrast` ≥ 3:1, `--contrast--low` decorative.
- [x] **Single default.** One Sass map each for colour-input, blend, opacity, contrast-blend (100/90/80%) and disabled defaults, used only as `@property` initial values. Delete the `$palette-defaults` duplication and the literal fallbacks in `generate-theme-*-defaults` (which today emit 84%/72% while the registered values are 90%/80%). `createTheme` emits a theme-level or per-palette variable only for keys the user passed: no re-emitted defaults, no `apply-density(0)`, so nested themes inherit correctly.
- [x] **Remove library-level Material aliases.** `--color--on-<palette>`, `--color--<palette>-container` and the other `generate-md3-role-aliases()` output leave the core; the demo and docs use `--color--<palette>--contrast` instead. Every Material-only role (X-container, fixed, inverse, scrim, shadow, surface-tint) comes only from the Phase 3 adapter, so there is one mapping, not two.
- [x] **Delete dead code.** Replace the deprecated Sass `if()` function calls in `_color-variants.scss` (lines 237, 238, 315, 316) with `@if` blocks or the modern syntax so builds stop warning. The seven uncalled `generate-*` mixins in `_color-variants.scss`; `density-selectors()` and its call; `_typography.scss` and `createTheme`'s `typography` key (`@error` pointing at `mat.theme()` if passed); `$set-material-vars` in `_palette-utils.scss`; unused `@use` lines. `apply-density` `@error`s outside 0..−3.

Done when: `pnpm test` passes and the demo shows the surface ladder in both modes with correct text on every surface.

## Phase 2 — Register inputs only

Goal: far fewer `@property` registrations, same features, theme crossfade intact.

Numbers (minified `core.css`, Verification step 4): before 714.0 KB, 29.5 KB gzipped, 1430 `@property` rules; after 561.9 KB, 24.8 KB gzipped, 32 `@property` rules.

- [x] **Register inputs only.** Register exactly the twelve colour inputs (`<color>`) and the theme-level tuning variables (`--theme--blend--*`, `--theme--opacity--*`, `--theme--contrast-blend*`, `--theme--disabled-*`, `--theme--density-scale`), all `inherits: true`, with the library default as `initial-value`. Unregister everything else: per-mode intermediates, joined `--color--*` leaves, contrasts, disabled, per-palette percentages.
- [x] `core()` emits `--theme--animatable: <comma list of the registered names>` so plain CSS can write `transition-property: var(--theme--animatable)`. Emitted on `:where(:root)` as a constant. Custom palettes from `createTheme` register their two inputs but are not in the list; name them in `transition-property` to crossfade them.
- [x] Record the trade-offs in the Animating chapter (noted in the chapter table for Phase 5): a light/dark flip does not crossfade (it is instant, as the OS flip is), and joined tokens are not animatable on their own. Measured in Chromium: the transition belongs on `:root` and on a `[theme]` element that switches its own theme. A nested `[theme]` that only inherits an input must not carry the transition: a transition on an inherited animating value restarts every frame and trails at about half speed (a 1 s crossfade settled after 2.2 s). Without it, the subtree follows the page in step, because derived tokens re-resolve from the inherited animating input. A derived palette on the same element (secondary from primary) does not trail: the after-change style excludes running transitions, so its end value is fixed. Contrast colours (`--contrast*`, `on-surface`) are a luminance step, so the text base flips black/white in one frame at the crossover; the fix is consumer-side, `transition: color 150ms` on the text elements, which smooths the flip and leaves the at-rest 4.5:1 guarantee intact. Where the flip lands depends on the colour: one whose luminance sits near the threshold flips its text near its own end of the crossfade, in the slow tail of the easing, so it can read as a late pop (measured: ember's secondary flips at 1.25 s of a 1.5 s crossfade going towards ember, at 0.38 s going away). Expected, not a defect.
- [x] Gain to document in the Light and dark chapter (noted in the chapter table for Phase 5): because unregistered `light-dark()` resolves where it is used, `color-scheme` on any element flips its subtree, with no `theme` attribute needed. Seen in Chromium on the demo's `crossfade.html` (panel 5); Firefox and Safari checked by hand.

Done when: the `@property` count equals the twelve colour inputs plus the tuning variables (printed by Verification step 4), the before/after gzipped size and count are in the commit message, and a manual crossfade between two themes, including a nested `[theme]`, animates in Chrome, Firefox and Safari. _Status 2026-11-07: count and numbers done. The crossfade page is chapter 13's example (`projects/docs/src/examples/13-animating.html`); measured in headless Chromium and Firefox: the page theme, the inheriting nested theme and the `color-scheme` panel are mid-way at 0.6 s of 1.5 s and the nested panel matches the page sample exactly, the self-switching nested theme moves only with its own button, and a mode flip is at its end value within 60 ms. Safari is still to be checked by hand._ _Status 2026-11-08: count and numbers done; the crossfade is chapter 13's example, verified in Chromium and Firefox (mid-way at 0.6 s of 1.5 s, inheriting nested theme in step, mode flip snaps). ## Phase 3 — Material adapter computed from Material's tables

Goal: an adapter derived from Material's own role tables and verified against real components.

- [ ] **Adapter computed in Sass.** `material-adapter.scss` `@use`s `@angular/material/core/tokens/m3/md-sys-color` and calls `md-sys-color-values-light($palettes)` and `-dark($palettes)`, where `$palettes` maps palette → tone → `tone(var(--theme--<mode>--color--<palette>), T)` (the Phase 1 function). It zips the two results into `--mat-sys-<role>: light-dark(<light>, <dark>)`. Rules on top of the tables: a role `core()` already defines maps to `var(--color--<role>)`; `on-<palette>` maps to `var(--color--<palette>--contrast--high)`; `-fixed` roles use the light input in both modes. Also emit `--mat-sys-neutral10` and `--mat-sys-neutral-variant20`, which Material's `_system.scss` adds separately and form-field and sidenav read.
- [ ] The adapter is emitted under `:where(:root, [theme])`, the same selector as `core()`, never `:root` alone, so every themed element re-maps `--mat-sys-*` and Material sub-theming works.
- [ ] Non-colour: the adapter emits only `--mat-sys-level0..5: var(--elevation-0..5)`. `mat.theme()` without colour still emits shape and state-layer tokens and omits elevation, so the adapter emits no shape or state tokens. Typography and density come from `mat.theme((typography: …, density: …))`.
- [ ] **`material-demo` project.** A minimal Angular app with a page of common Material components (buttons, form fields, cards, menu, dialog, tabs, lists). It depends on the library via `workspace:*`, imports only through its exports, and lists styles in this order: `core.css`, `material-adapter.css`, then `styles.scss` containing `mat.theme((typography: …, density: …))`. It has a nested `theme` region whose menu and dialog put `theme="x"` on the panel (overlays render outside the subtree). `themeSwitcher` is used from `afterNextRender`. `docs/build.ts` copies its `ng build` output to `dist/material/` for the Angular Material chapter's iframe.
- [ ] Bump Material to 21 (a rebuild picks up its tables).

Done when: `material-demo` looks right in light and dark across three themes plus the nested region, and the Angular Material chapter is written.

## Phase 4 — Runtime: switcher and data-driven themes

Goal: the smallest possible JavaScript surface for runtime theming. No colour maths in JavaScript, ever.

- [x] Keep `ThemeSwitcher` with four changes: `setColorScheme('auto')` removes the inline style (core's `color-scheme: light dark` does the rest; delete the matchMedia listener); `restoreTheme` sets the saved attribute unconditionally (CSS picks it up when the rule arrives); `setTheme` drops its unknown-theme check; the `themeSwitcher` singleton is created only when `typeof document !== 'undefined'` (SSR-safe import).
- [x] `defineTheme(name, vars)` takes a flat object whose keys are the documented input variables, e.g. `{"--theme--light--color--primary": "#3f51b5"}`: only `--theme--*` keys, the six standard palettes plus tuning. Custom palettes are Sass-only. Implementation: append one `<style data-theme=name>` to head, `sheet.insertRule('[theme="' + CSS.escape(name) + '"]{}')`, `rule.style.setProperty(k, v)` per entry (no string-built CSS); colour values failing `CSS.supports('color', v)` are skipped with `console.warn`; then call `discoverThemes()`. `removeTheme(name)` removes the element, clears the attribute if that theme is active, and calls `discoverThemes()`.
- [x] A three-line head script, shown in the Runtime chapter, applies the stored theme and scheme before first paint (no flash of the wrong theme).
- [x] Storage key migration from the old `cpngTheme` keys is not done; this is a breaking release.
- [x] Storage is per origin, so the docs site and its example iframes share the stored choice. The switcher sets a stored name even when the page has no rule for it (a rule may arrive later); the site chrome and the chapter 12 example list such a name as "(no rule on this page)" rather than showing a blank select.

Done when: the Data-driven chapter example loads themes from a JSON fixture (one row with an invalid colour that warns), nests one inside another, and restores it after reload; the Runtime switching and Animating chapters are written. _Status 2026-11-07: done; verified in headless Chromium and Firefox (fixture loads with exactly one warning, page and nested theme restored after reload, head script applies the attribute while the document is still parsing)._

## Phase 5 — Documentation site

Goal: a static site, built with the library itself, where every page is a working example of what it teaches.

### Site mechanics (KISS)

- `projects/docs/src/` holds one HTML file per chapter, `chrome.css`, and `examples/`.
- Each example is a standalone page `examples/NN-name.html` plus its own optional `.css`, `.scss`, `.js` or `.json` files, rendered in an `<iframe>` with the escaped source of those files beneath it. `<!-- include: examples/<file> -->` works for any extension; a missing file, or a chapter with no example, fails the build. Sass compiles non-partial `examples/*.scss` to `dist/examples/*.css`.
- An example loads only `core.css` (and later the files of the chapter it belongs to). `theme-switcher.js` is loaded by the site chrome and by examples from Runtime switching on. Example styling never lives in `chrome.css`. Site chrome never shares a document with an example.
- Navigation is a plain list. No client-side framework. `simple-theming-demo` is deleted when the docs site builds.
- `build.ts` also generates the Reference page from the compiled `core.css`.

## Decisions already made (so they are not reopened)

- Inputs-only `@property` registration; light/dark flips are instant, theme changes crossfade.
- Contrast is chosen by WCAG luminance in CSS; there is no contrast override hook until someone needs one.
- The adapter is Sass computed from Material's tables; no Node generator, no committed generated file.
- Surfaces use the `tone()` formula with Material's tone numbers; the same function feeds the adapter.
- No stress page or single-pass `light-dark()` experiment: with about 32 registrations, recalc cost is moot, and single-pass would raise the browser baseline.
- Custom palettes are Sass-only; `defineTheme` covers the six standard palettes plus tuning.
- Docs are deployed to GitHub Pages; the Gallery is replaced by the generated Reference page.
- Releases run through cpdevtools/git-flow: placeholder versions, release PRs, npmjs only (no GitHub Packages publish), the rewrite on `feature/ng21`, graduation to `main` at 21.0.0.
