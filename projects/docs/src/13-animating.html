Animating theme changes

One declaration makes a theme change crossfade, every token at once. The rule is where to put it, and what will not fade.

Press the page button: every swatch, the gradient, the coloured part of the shadow and panels 4 and 5 crossfade over 1.5 s. Panel 3 moves only with its own button. The mode buttons snap.

Why a theme change can crossfade

A custom property is a string to the browser, and a string cannot be animated. core.css registers its input variables from chapters 3 and 10, the twelve colours and the tuning values, with @property and a type, so the browser can interpolate them. Nothing else is registered. When theme="indigo" becomes theme="ember", the inputs change, and if a transition covers them, they move from one value to the other; every token is derived from the inputs, so every token moves with them. The Reference page lists the registered inputs.

The declaration

:root {
  transition-property: var(--theme--animatable);
  transition-duration: 1.5s;
}

--theme--animatable is a constant core.css emits: the comma-separated names of all the registered inputs. Using it keeps the list out of your code. transition: all would not do: custom properties are not part of all.

Where to put it

On :root, and on every element with a theme attribute that switches its own theme, like panel 3. The example's rule is :root, [theme] { … }, which covers both.

Never on a nested theme that only inherits its inputs, like panel 4, which sets only tertiary. Its primary is inherited from the page, and while the page's primary is animating, the inherited value changes every frame; a transition on that element would start over every frame and trail behind at about half speed (a 1 s crossfade settling after 2.2 s). Without one, the panel follows the page in step, because its tokens re-resolve from the inherited animating input. That is the .inherits rule in the example, which turns the transition back off.

A derived palette on the same element does not trail: panel 1's secondary is worked out from its primary, and both arrive together.

What does not crossfade

  • A light/dark flip. color-scheme changes which half of each light-dark() is used; no registered value changes, so nothing interpolates. The flip is instant, as an OS flip is.
  • A token set directly. Write --color--primary: red yourself and it snaps, because the token is not registered; only the inputs are. Change the input instead.
  • A custom palette (chapter 8). Its two inputs are registered but are not in --theme--animatable; name them in transition-property after the variable to include them.

Text at the crossover

Contrast colours (chapters 1 and 4) are black or white, chosen in CSS by a luminance step. As a swatch fades from a dark colour to a light one, its text flips from white to black in one frame when the swatch crosses the threshold. The example smooths that with transition: color 150ms on the text elements, which is a transition on an ordinary property and leaves the 4.5:1 guarantee at rest untouched. A colour whose luminance sits near the threshold flips near its own end of the crossfade, in the slow tail of the easing, and can read as a late pop. That is the step doing its job, not a defect.
